## 一、方向级（4 项）— 最该先拍板

### 1. V1 到底是"纯对话"还是"对话 + 记录本"？

- **冲突**：BACKLOG 的 V1 定位 = 案件记录本最小版（Vera 手动写，系统自动累积）；主文档 = 对话优先（她大部分时间在 BrainChat）。两种模式交互完全不同。
- **架构影响**：决定前端骨架、录入入口（聊天管道 vs 手动表单直写事件）。两条路数据模型一样（都汇入 CaseContextEvent），但入口与 AI 依赖度不同。
- **Vera 视角**：她已日常高频与 AI 聊天（零学习成本）；但"复制邮件内容快速贴进去"的场景，记录本比聊天更可靠（不怕 AI 提取错）。
- **倾向**：对话为主 + 记录本保留为"快速粘贴"快捷入口（混合模式，前端成本不高）。
- **✅ 已定稿（2026-08-12）**：**对话为主的三栏布局**（AI First 案件上下文工作台）——
  - 左栏：案件/会话列表（≈240px，可折叠 60px）——一个案件 = 一个对话线程；
  - 中栏：BrainChat 主对话（最宽）——AI 从悬浮球变主角，混排对话气泡/工具卡/草稿卡；
  - 右栏：客户全景（≈360px，可折叠）——"AI 知道什么"可视化：事实卡/摘要/时间线/待办/统计；
  - 默认页 = 最近案件对话；任务/看板/统计/设置降级为左栏底部次级入口；
  - 参考形态：Claude Projects / ChatGPT Projects / Cursor per-repo chat 收敛出的同一模式；
  - 前端改造按 AI Studio 批次执行（批 F-1 起），Apple 设计规范融入动画与材质。

### 2. 防串案协议（记错客户 = 灾难）

- **问题**：Vera 一天聊几十个客户，AI 如何知道"现在说的是谁"？记错客户 → 写错邮件/给错建议 → 红线事故。
- **架构影响**：对话会话需绑定案件（CaseChatMessage.session_id 现在固定=case_id）；需切换协议 + AI 回复带客户确认 + 名称匹配建议绑定。
- **Vera 视角**：零歧义——对话标题显示"当前客户：张三（CBA）"，AI 每次回复开头带客户名；全局对话不涉及具体客户。
- **倾向**：每个会话强制绑定一个案件；点名客户时 AI 必须先确认绑定。
- **✅ 已定稿（2026-08-12）— 三层防线协议**：
  - **① 结构性绑定**：一个案件 = 一个对话线程；中栏 BrainChat 只接收当前选中案件 caseId，发消息必带 case_id；中栏顶部常驻"当前客户：张三（CBA）"，案件切换有明确视觉变化（标题/颜色/面包屑）。
  - **② 事实归属校验**：AI 提取事实只归当前会话绑定案件；对话中出现不匹配客户名 → 弹建议卡"这条信息看起来属于李四（NAB），要切换吗？"——**未确认不写事实、不进蒸馏**；与 S1 的客户匹配确认合并为同一套规则。
  - **③ 外线强制确认**：草稿卡生成时必须有客户名确认"以下草稿将发送给 NAB，收件客户：张三（CBA）——确认？"；与双线披露防线叠加。
  - **全局对话边界（已定）**：允许通用咨询 + 只读查询（回答必须标注客户名）；**禁止**在全局对话写事实、生成外线草稿。写入必须发生在明确归属的案件对话。
  - **回复带名规则（已定）**：日常问答不加，涉及事实确认/外线草稿/记录动作时以"张三（CBA）"开头；中栏顶部常驻客户名是基线。
  - **切换交互（已定）**：左栏点案件 = 切换会话（A 方案），切换是明确导航动作，不依赖 AI 理解；对话中提到其他客户走"提示切换，不写入"。

### 3. 主动询问的触发时机（"AI 主动问"是 Phase 1 灵魂）

- **问题**：什么时候开口？打开对话就问？检测到事实缺口才问？"上次说周三交合同，交了吗"——前提是 AI 记得"周三交合同"这个承诺，但**当前没有任何承诺/截止日提取机制**。
- **架构影响**：需要事实缺口检测（BrainFact 缺失字段 vs 画像 schema）+ 承诺/截止日提取（新事实类型）+ 提醒调度。
- **Vera 视角**：问多了烦（打扰），问少了没用。节奏要克制：建案问 1-2 个，跟进只在承诺到期/缺口出现时问，可一键关闭。
- **倾向**：V1 先做"被动问答 + 承诺提取"，主动询问只做建案流程；跟进询问等承诺机制稳定再开。
- **✅ 已定稿（2026-08-12）— 对话触发 + 表单/流程页模式（Vera 提出，优于对话内逐问）**：
  - **核心模式**：AI 识别意图 → 回复"开始"按钮 → 弹出结构化表单页（可贴一段话识别预填）→ 保存 → 回写对话 + 全景。对话负责触发与理解，页面负责结构化录入。
  - **三级分级**：L1 轻输入（字段≤3、开放式）→ 对话内直接完成（记一笔/问进度）；L2 结构化录入（字段多/含识别）→ 按钮+表单页（建案/存量建档）；L3 多步流程（有进度/选材料/多步）→ 按钮+流程页带步骤条（一致性检查/催件）。判据：字段数 ≥4 或需识别/确认/多步 → 弹页面。
  - **表单形态**：Apple 风格底部 sheet（从下往上滑出，可下滑关闭），临时任务不改变三栏上下文；视觉打磨时可调。
  - **中断恢复**：表单草稿自动存 localStorage，关闭后再次进入同入口提示"检测到未完成草稿，继续？"；V1 不做后端草稿表，V2 多设备再上云。
  - **一段话识别**：放在表单页内——贴一段话 → 调后端 createCase(raw_text) 解析预填 → 她确认修改 → 提交；不经过对话，避免两段式。
  - **L3 步骤条**：Step 1 选择材料 → Step 2 分析 → Step 3 结论，每步可保存可中断，返回从断点继续（契约先行，施工放 F-3 后）。
  - **V1 主动询问范围**：只做"对话触发 → 页面"两类（建案/存量建档 L2、一致性检查 L3）；承诺到期提醒（场景 C）依赖承诺提取，V2 再上。

### 4. 旧工作台去留（任务队列/案件看板/草稿箱/档案库/导入/知识中心）

- **问题**：大脑模式下"任务卡从主界面撤下"，那草稿箱/档案库/导入/知识中心留不留？批 D 刚实化过四个空壳页，若 V1 不露等于白做。
- **架构影响**：前端从"任务工作台"重写为"大脑"——页面裁剪、路由精简；后端任务引擎保留后台当 AI 的待办模型。裁剪不删代码，只隐藏入口。
- **Vera 视角**：突然全撤会慌；但她要的是"面对事，不面对模块"。
- **倾向**：V1 界面 = 对话 + 客户全景 + 统计（天/周/月）；草稿箱藏二级入口（写邮件从对话内出草稿）；档案库/导入藏起。
- **✅ 已定稿（2026-08-12）— 左栏底部入口结构**：
  - **"任务"重定义为"待办"**：旧任务队列（邮件/文件/OS 管道卡）在新框架下不再产生内容，左栏不放"任务"，放"待办"= 手动任务 + AI 建议待确认（承诺/跟进 V2 再加）；点一项跳到对应案件对话继续处理。
  - **左栏底部 4 入口**：统计（Analytics 天/周/月）· 看板（CaseBoard）· 待办 · 设置（Settings 含能力中心入口）。
  - **知识中心**：V1 收起（能力中心→设置里；政策库等 #14 建起来再以"政策库"回归）。
  - **草稿箱**：藏"更多"作兜底；主入口是对话内草稿卡。
  - **档案库 / 导入历史 / 数据迁移**：藏"更多"（低频，不占主入口）。

## 二、架构级（8 项）— 需要细化设计才能出施工单

### 5. BrainFact 的 key 词表谁来定

- **问题**：BrainFact 是"可查询 KV 事实"，但 key 若由 AI 自由生成，"income / monthly_income / 收入"并存，跨案件无法查询与统计。
- **架构影响**：需 config/fact_schema.yaml 定义 category+key 枚举（如 income.monthly_payg、liability.debt、bank.lender）；LLM 提取只能映射词表内 key；新 key 走申请流程。
- **Vera 视角**：感知不到词表，但感知"AI 记的收入对不对、能不能查到"。词表稳定 = 全景/统计准确。
- **倾向**：第一版 30-50 个 key，覆盖建档项 + 承诺 + 阶段 + 银行 + 金额类；金额/日期/银行名用规则锚定。
- **✅ 已定稿（2026-08-12）— 受控词表规则**：
  - 词表放 `config/fact_schema.yaml`（与 checklist_master.yaml 同模式），配置驱动 + 版本管理；
  - AI 提取只能映射词表内 key，禁止自造；词表外概念 → 存 `unclassified` + 原文摘要 → 对话轻提示"有 1 条未归类信息，归到哪？"或忽略；
  - 新 key 由维护者按施工单加（Codex/opencode），不开放 AI 自由加；金额/日期/银行名用规则锚定（正则/枚举），不依赖 LLM；
  - 第一版词表见文末附录 A（**42 个 key**，✅ 已确认 v1，2026-08-12 Vera 拍板"按草案走"；配置驱动，试用期可迭代）。
- **✅ 施工完成（2026-08-12，WO-15）**：fact_schema.yaml（42 key 全量转译）+ brain_facts 表（迁移 354973fd6c37）+ 规则锚定（bank.lender/stage.current，金额只出证据）+ LLM 词表提取（脱敏→白名单→unclassified，失败降级）+ sync 幂等/冲突 supersede/事件撤销置 valid_to + GET facts / POST facts-sync 端点；全量 pytest **479 passed**（基线 464 + 新增 15，零回归）。

### 6. 确认闸门的落点（高置信直接记 vs 低置信反问）

- **问题**：CaseContextEvent 表**当前没有 status/confirmed 字段**（已核实）——待确认事实放哪？
- **架构影响**：方案 A：事件加 status（pending/confirmed/superseded），已确认不可变，纠正 = supersede + conflict；方案 B：先存对话层，确认后才写事件。账本不可变原则下倾向 A。
- **Vera 视角**：最烦"记对了还要逐条确认"；最怕"记错了没告诉她"。
- **倾向**：高置信（金额/日期/银行/明确姓名）直接记 + 对话尾部"📌 已记录 N 条 [查看]"可一键撤销；低置信插入轻确认。
- **✅ 已定稿（2026-08-12）— 事件状态机（pending → confirmed → superseded）**：
  - CaseContextEvent 加 `status` 字段：pending（待确认）/ confirmed（入账本）/ superseded（被取代，保留审计）；
  - **高置信**（金额/日期/银行名/明确姓名，rule 锚定）→ 直接落 confirmed + 对话尾部小字"📌 已记录 N 条 [查看]"可逐条撤销（轻量，不弹窗）；
  - **低置信**（判断句/模糊表述，LLM 提取）→ 落 pending + 对话内轻确认卡（"记成 $9 万对吗？[确认][修改]"），确认 → confirmed；
  - **撤销/纠正** → 不物理删除（账本不可变红线），写 superseded 事件指向旧事件；新事实替代旧事实，旧事实可审计可恢复；
  - **status 与 track 正交**：pending/confirmed 跟随 internal/external 双线；
  - 蒸馏/全景/BrainFact 只从 confirmed 事件重建，pending 不参与（隔离"AI 猜测"与"Vera 确认的事实"）。
- **✅ 施工完成（2026-08-12，WO-14）**：迁移 `b4e1c9d2f7a3`（case_context_events 加 status/superseded_by/supersede_reason，历史行默认 confirmed）；蒸馏只从 confirmed 重建；3 端点（列表 status/track 过滤、confirm 幂等、supersede 审计撤销，404/409/422 全覆盖）；全量 pytest **464 passed**（基线 455 + 新增 9，零回归）。

### 7. 对话记录 ↔ 事实的衍生关系

- **问题**：L0 对话 → 事实（事件/蒸馏）单向派生。Vera 说"删掉那句/纠正一下"，已写入的 BrainFact、摘要要不要级联重建？
- **架构影响**：账本为王原则下，对话不是账本、事件才是；删对话 ≠ 删事实。需要"事实级撤销"（supersede）而非"对话级删除"，并定义重建/失效链路。
- **Vera 视角**：她删对话通常因为"记错了"，期待事实也消失；若删了不生效会困惑。
- **倾向**：提供"撤销记录"按钮（事件级 supersede）；删对话时提示"事实仍在，如需删除请点撤销"。
- **✅ 已定稿（2026-08-12）— 三层分离，不做级联删除**：
  - **L0 对话**：可删，只影响聊天展示，不触发下游（对话是原料，事实是确认后的产物）；
  - **L1 事件（事实）**：可撤，走 #6 superseded 状态机，不物理删除；撤销入口在"📌 已记录 N 条 [查看]"逐条操作；
  - **派生层（BrainFact/摘要/全景/向量）**：不手动删，只重建——全部从 confirmed 事件派生，事件变更 → mark dirty → 懒刷新（沿用 WO-09 机制）；
  - **撤销传播规则**：撤一条 confirmed 事实只影响它自己 + 依赖它的派生层，**不连坐**同批其他事实；新旧矛盾 → 旧 superseded + conflict 标记，全景显示"⚠️ 已更新（12 万，8 月 12 日更正）"可看变更历史；
  - **删对话提示（已定）**：删聊天消息时若含已确认事实 → 轻提示"这条对话含 2 条已记录事实，要同时撤销吗？[仅删对话][一并撤销]"；无则直接删；
  - **刷新策略（已定）**：懒刷新（沿用 dirty 机制）——全景/摘要打开时刷新；**AI 对话注入时强制用最新**（回答正确性依赖最新事实）。

### 8. 上下文注入的具体分配（≤2000 tokens）

- **问题**："检索 → 排序 → 注入 ≤2000 tokens，按任务类型选择"——BrainFact 关键事实/一句话摘要/最近 3-5 事件/相关经验各占多少？全局对话注入什么？
- **架构影响**：需定义注入协议：任务类型（咨询/写邮件/总结/建案）→ 检索策略 → token 预算分配（如关键事实 800 / 摘要 200 / 事件 500 / 经验 300 / 系统提示 200）。
- **Vera 视角**：决定"AI 知不知道这个客户"。预算太小记不住，太大费钱变慢。
- **倾向**：V1 固定协议手工调参，用她 10 个真实问题做验收（都能答对/答到点上）。
- **✅ 已定稿（2026-08-12）— 会话记忆分层注入协议 + DeepSeek 缓存友好结构**：
  - **现状问题**：现有 POST /api/chat 每次只传当前消息 + 案件快照，**历史对话一条不传**（前端历史只是给 Vera 看的）——AI 每轮"失忆"，这是比 token 爆炸更紧急的缺陷。
  - **每次调用注入五层（缓存友好排序，✅ 2026-08-12 拍板）**：① 角色 prompt（300）→ ② 案件大脑/摘要（1800）→ ③ 团队经验/政策要点（1500）→ ④ 实时数据（3000）→ ⑤ **对话追加区**（最近 N 轮原话，约 500 tokens，待施工）；前缀顺序固定，命中 DeepSeek 上下文缓存（命中价 ≈ 1/10~1/120）。
  - **缓存决策 1（✅ 2026-08-12 拍板）— 追加式 + 折叠式，替代滑动窗口**：滑动窗口从头部切会毁掉前缀缓存，改用**追加式消息结构**——新消息永远接在尾部；窗口超长时把**最早一段已确认内容折叠进蒸馏摘要**（写入 context_summary，账本 CaseContextEvent 不变），折叠后前缀保持稳定。折叠只对"已确认/已蒸馏"内容，未确认对话原样保留到确认或自然超窗。
  - **缓存决策 2（✅ 2026-08-12 拍板）— 缓存友好排序定进注入协议**：层序固定为 角色 → 案件大脑/摘要 → 经验/政策 → 实时数据 → 对话追加区；对话追加区永远在最后，任何一层内容变化只影响其后缀，前缀仍可命中缓存；层序作为协议参数由施工单钉住，观察期可依命中率数据微调（改排序 = 改施工单，不静默改）。
  - **压缩哲学**：对话原话不是真相源，账本才是——旧对话里确认过的内容已蒸馏进案件大脑/摘要，折叠掉的是"已确认内容"而非记忆，不伤上下文。无感知折叠，不向 Vera 暴露"压缩"概念。
  - **翻篇方案（已定）**：V1 用方案 A——同一案件单线对话，追加式 + 折叠兜底，无新会话概念；V2 再考虑"咨询/递交"双线程（方案 B），与双线模式合并设计。
  - **测量工具（已定）**：不设预算硬限制，只设超量预警（7 天基线 3 倍，阈值可配置）；ai_usage_log 记录各层 token/延迟/费用 + 质量信号（纠正次数），复用 analytics 天/周/月框架；观测期 1 周对齐试用。
  - **缓存命中率指标（✅ 2026-08-12 拍板）**：网关记录 DeepSeek 返回的 prompt_cache_hit_tokens / prompt_cache_miss_tokens，测量工具加"缓存命中率"维度——命中率高 = 前缀稳定有效，是省钱的核心杠杆。

### 9. 递交模式怎么进、disclosed 开关谁按

### 15. 存量客户壳建档

- **问题**："存量客户可建壳（客户名/银行/金额/一句话）"——谁来建？流程没写。
- **架构影响**：壳 = 最小 Case（客户名/银行/金额/一句话）+ legacy 标记；后续聊天补充。需"建壳"入口（对话或表单）。
- **Vera 视角**：老客户都在她脑子里，不建壳 AI 帮不上忙；建壳成本必须极低（一句话触发）。
- **倾向**：对话里说"给张三建个壳"→ AI 问 3 个问题 → 建好；历史资料不迁移。
- **✅ 已定稿（2026-08-12，第一轮）— 存量活跃客户：三级建壳 + 动作驱动补全**：
  - **问题再定义（Vera 提出）**：活跃存量客户"从半截进来"，AI 最该知道三件事：**现在卡在哪一步 / 下一步是什么 / 有没有坑（注意事项）**——不是先补全字段。
  - **三级建壳（Vera 认可）**：
    - **极简壳（30 秒）**：客户名 + 一句话——低频/可能回来的客户；
    - **标准壳（1 分钟，活跃客户默认）**：客户名 + 银行 + **现在卡在哪一步** + 一句话（如"NAB 在审，等 OS 条件"）；
    - **完整壳（2-3 分钟）**：+ 金额/收入类型/签证/注意事项——知道多少填多少，缺的不判错。
  - **量级**：活跃客户约 28 个——按需建壳（处理到谁建谁），支持"建档冲刺"（某天集中处理几个）。
  - **动作驱动补全（核心机制）**：不靠 Vera 专门补全——每次日常交互（写邮件/问进度/转述银行回复）AI 顺手提取事实进账本，壳越用越完整（"越用越完整"而非"先补全再用"）。
  - **全景补全进度灰提示**：缺关键信息（收入/签证/负债）灰色展示，不红不弹窗；AI 只在相关对话时机轻问，不专门打扰。
  - **AI 带不确定性工作**：信息不全也能干活——知道就答，不知道明确说"这个客户我还没记 X"，绝不瞎编。
  - **数据模型**：壳 = 普通 Case 少字段，`is_imported=True` 标记存量；无"转正"仪式，聊天补充自然长全；补了收入类型后触发 #13 清单预选。
- **✅ 已定稿（2026-08-12，第二轮）— 文件识别提取 + 统一建案页（Vera 拍板结构）**：
    - **机制可行（底层已核实）**：liteparse 2.11.1 已装（PDF+OCR 本地解析），core/pipeline/parser.py 现成；链路 = 扔文件 → 本地解析（不出网）→ 脱敏 → LLM 按 fact_schema 提取（#5）→ #6 确认闸门 → 进账本 / 预填表单。
    - **关键文件 → 字段**：payslip → 收入/雇主/ABN；银行对账单 → 负债/余额/存款来源；签证信 → 居住状态；现有贷款账单 → 负债明细/利率。
    - **边界**：只提取事实字段，**不做行为推断**（"孩子相关支出"等信号留给申报一致性检查，按需触发）；V1 以 PDF 为主，扫描件/图片 OCR 实测后再放开。
    - **统一建案页**：新客户建档（#13）/ 存量壳（三级）/ 历史导入 **共用一个弹窗**——顶部 = 文件解析导入口（扔几个关键文件）；中下部 = 字段表单（解析结果预填、可改）；同时支持一句话解析预填（#3）；确认 → 创建案件。
    - **触发与全局约束（Vera 观察确认）**：建案/导入是"无案件上下文"的全局动作，只能从全局 AI 聊天窗口（或左栏"＋新案件"）触发；**创建成功后自动进入该案件对话**（上下文就绪）；#2 全局对话"禁止写事实"不适用于"创建案件"本身——创建后写作自然转入案件对话。
- **✅ 后端已落地（2026-08-13，WO-18）**：parse-file 端点（liteparse 本地解析 → 脱敏 → LLM 提取 → 预填字段，临时文件清理、不建索引不留全量）；parse-text 端点（一段话识别）；前端表单导入口待 F-7。
